Can generative audio meet a real-time game latency target?

I built a playable UE5 prototype to measure whether generated sound can keep up with gameplay.

A gameplay sound has roughly 150 milliseconds before the player hears it as late. Raw AI generation needed seconds. The version that works stops generating during gameplay and prepares sound before the player needs it.

The experiment

A game that asks for its own sound effects

The prototype is a small UE5 level that requests sound while you play it. When something happens in the game, the Unreal client sends a text description to a Python server over a websocket. The server loads the model, checks its cache, generates audio if it has to, and streams PCM back for Unreal to play.

That round trip is the whole thesis. Every request was timed from game event to first audible sample, across four generation methods: procedural DSP, AudioGen and MMAudio running locally, and ElevenLabs in the cloud.

I built both ends myself: the C++ client in Unreal, the Python server, the cache, the retry handling and the benchmark logging. The numbers below come from that setup, not from model spec sheets.

Why latency matters

You kick a door and the room stays silent. You are already two steps into the corridor when the bang finally lands behind you. In play, a correct sound that arrives late reads as a missing sound.

Method and limits

Mid-tier hardware, warm and cold runs

The test machine used an AMD Ryzen 9 7940HS, RTX 5070 Laptop GPU with 8 GB VRAM, 64 GB RAM, Unreal Engine 5.4.4 and Python 3.11.7.

The 600 timed generations covered cold starts and warm inference for standardized 0.5–2.0 second clips. Local models ran on the same GPU; ElevenLabs included network time. The 100–150 ms line is the project's interaction target, grounded in the latency literature cited in the thesis.

Quality testing used 60 loudness-normalized samples across 12 prompts and five methods. Method names were hidden during rating, but one person rated the set, so those scores are directional rather than a multi-listener MOS study.

What worked

Stop generating during gameplay

None of the tested models fit the playable window, so the pipeline moves generation off the critical path instead.

The version that works never generates a sound the moment the player needs it.

Instead, the server watches game state and predicts what is likely next: the player approaching a door queues door sounds, entering a forest queues ambience. Generation happens off the critical path, and the results land in a cache keyed by the request.

When the event fires, the sound is already there and plays instantly. If the prediction missed, procedural DSP covers the moment at 15–25ms while the real sample generates for next time.

The pipeline Predict what the player will need → generate off the critical path → cache the result → play instantly → DSP covers the misses.
