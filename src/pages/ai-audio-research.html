AI Audio Research

AI audio arrived late. I built a UE5 prototype to test a runtime version of AI game audio: no giant banks of repeated footsteps, just sounds made when the game needs them. The result was blunt. The models sounded usable, but they arrived after the moment had already passed. The useful discovery was not faster generation. It was caching.

01 / The failed assumption

I started with the wrong verb: generate.

Here is the thing about game audio: most of it is still files. Somebody records or designs a footstep, gunshot, UI click, or explosion, exports it, names it, and ships it. A big game can carry thousands of these files. Gigabytes of “sword hits metal.”

The AI version sounds tempting: a player steps on gravel, the game sends “short gravel footstep,” the model makes a fresh variation, Unreal plays it. No huge audio bank. No repeated footsteps. Nice idea. The problem is timing. If a gunshot arrives 100ms after input, players feel it. My fastest local model still needed 1.4 seconds on first playback.

input 150ms 1.4s+

For first-playback SFX, “better quality later” loses to “rough sound now.”

test 01

Wire UE5 to a generation server.

Unreal talks to a Python backend over WebSocket. Python loads the models, juggles VRAM on an 8GB GPU, creates raw PCM, and sends it back to the engine. This is where the clean research question turned into thread ownership, model warmup, cache misses, and requests arriving in bursts.

test 02

Stop listening emotionally. Measure the wait.

I tested 24 prompts across footsteps, impacts, UI clicks, ambience, and music. Five methods, five repeats, 600 benchmark generations. Then 500 stress-test attempts per method to see how often things break. The quality scores were useful, but latency made the decision.

Then I looked at the cache logs.

Every model failed the speed test. MMAudio Small still needed 1,400ms. That is roughly 85 game frames. I had added caching just to stop regenerating the same prompt. Then the logs showed cache hits landing inside the interactive window. Wait. That was the first useful result.

03 / Model bench

Click through the methods. None of them wins alone.

Quality scores are my 1-5 evaluation across prompt match, clarity, transient detail, and usefulness in-game. The point is not “which model is best.” The point is which job each method can safely do.

Fallback

Procedural DSP

15-25ms / quality 2.4/5 / 0% failure

No GPU, no network, just math. It sounds simple and low-fidelity, but it never lags and never goes silent. That reliability is why it belongs in the fallback chain.

Local ambience

AudioGen

2.1-2.8s / quality 3.6/5 / 9.2% failure

Meta's text-to-audio model. The most predictable local ambience option in my tests: useful for wind, rain, and ambient beds, but plain on sharp transient sounds and too slow for first-playback feedback.

Local texture

MMAudio Large

2.6-3.4s / quality 3.9/5 / 13.8% failure

Best sounding local model. Good textures, less synthetic than AudioGen, but 3.1GB of VRAM means almost nothing else fits beside it. Model swaps cost 2-4 seconds, and short duration control was unreliable.

Best local tradeoff

MMAudio Small

1.4-1.9s / quality 3.5/5 / 7.2% failure

The lowest local median latency. Faster than Large, still decent, and at 1.8GB it can share VRAM with AudioGen. It was the only local model that made sense for predicted ambience or cached content.

Cloud quality

ElevenLabs

1.8-3.5s / quality 4.3/5 / 4.8% failure

Best subjective output by a clear margin: sharper transients, cleaner results, sometimes close to a real recording. But latency varied from 1.8 to 3.5 seconds, outside the first-playback budget. Great for pre-generation, wrong for immediate gameplay feedback.

04 / Production problems

The production problems were the real test.

Unreal thread ownership

USoundWave creation has to happen on the Game Thread. I used FFunctionGraphTask so PCM creation did not sit inside the WebSocket callback path, then tested 50+ sounds arriving at once.

VRAM budget

UE5 rendering left roughly 3GB for AI on an 8GB GPU. The backend checks free memory with NVML, unloads cold models, and keeps frequently used models resident in sticky mode.

Failure handling

Models failed 5-14% of the time. The fallback chain retries with a new seed, tries another model, plays procedural DSP, or skips the sound instead of freezing the game.

Bleeding-edge hardware support

TangoFlux would not start because PyTorch 2.4 / CUDA 12.4 had no compiled kernels for the RTX 5070's Blackwell chip. That was a useful warning about building on fresh research code.

05 / Answer

I would not ship “AI generates every SFX instantly.” I would ship a preparation system.

Raw AI: no. Every model exceeds the first-playback budget. With caching: yes, if the sound already exists. With prediction: yes, if the game knows what it will need before the player needs it. The real answer is not one model. It is the right method for the right sound, cache everything useful, and always have a fallback ready for when things break.

DoGenerate before the player needs it.
DoCache every useful result.
DoKeep procedural fallback ready.
Do notBlock gameplay on a model response.
