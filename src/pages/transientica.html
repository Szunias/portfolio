The short version

The player records 10 examples of each beatbox sound. I turn every hit into 7 audio features, classify it with a KNN model written in C#, and judge its timing against windows as tight as ±60 ms.

The game

A rhythm game that has to learn the player first

Kick, snare and hi-hat do not sound the same from every person or microphone. A fixed set of rules would work for me and fail for somebody else, so Transientica begins with a short personal training session.

Once the model knows your sounds, the game can focus on the familiar rhythm-game questions: did you perform the right sound, and did it land close enough to the beat?

What the player actually does

You record a few kicks, snares and hi-hats. A song starts, notes approach the timing line and you perform the matching sound. The game identifies the hit, measures how early or late it was, then builds your score and combo.

From microphone to judgement

What happens after you make a sound

The entire path now runs inside Unity. There is no Python process, OSC connection or external machine-learning package between the microphone and the game.

Imagine you perform a snare just as its note reaches the timing line.

The microphone writes continuously into a pre-allocated ring buffer. An onset detector looks for a sudden rise above the room's noise floor, then sends a 512-sample window through my FFT.

From that window I measure spectral centroid, rolloff, flux, zero-crossing rate, RMS, attack time and flatness. KNN compares those seven values with the examples recorded during training and returns the closest sound class.

Finally, the game matches the hit to the nearest note using Unity's audio clock. It backdates the onset by roughly 5.8 ms for the analysis window, then judges both the sound and its timing.

The full trip Microphone → onset → 512-sample FFT → 7 features → KNN → nearest note → score.

Making it feel fair

Classification is only half the problem

A correct snare still feels wrong if the game reacts late or judges microphone delay as a bad performance.

Perfect is ±60 ms, Great is ±130 ms and Good is ±200 ms. Anything farther away becomes a miss.

Those windows run on AudioSettings.dspTime, not the visual frame rate, so the judgement is not limited by when Unity happens to draw the next frame.

Before playing, the user can beatbox along with calibration clicks at 100 BPM. The game measures the recurring offset and stores it; manual adjustment is available in 1 ms steps.

The combo multiplier grows from 1× to 8×, while the final result ranges from F to S. Notes are pooled ahead of time so spawning them does not allocate during the song.

The rebuild

Why the research prototype was not enough

The first version proved that beatbox classification could drive gameplay. Turning that proof into a standalone game required a different architecture.

One process instead of two

If Python stopped, Unity stopped hearing the player.

The prototype analysed audio in Python and sent classifications to Unity over OSC. It worked, but debugging crossed two runtimes and a standalone build would also need a Python installation.

I rewrote the FFT, feature extraction and classifier in C#. The current game has one executable, one audio path and no local network connection that can silently fail.

SVM to KNN

The accurate prototype model was awkward to retrain inside the game.

The Python SVM reached 92% accuracy, but training depended on scikit-learn and its saved model did not fit naturally into the Unity build.

I switched to inverse-distance KNN with K=5. Training mostly means storing normalized examples, so the player can retrain between rounds. The model saves as readable JSON and checks itself with leave-one-out cross-validation.

Prototype to game

Recognising beatbox sounds was interesting, but it was not yet something to play.

The research build could display a classification and run a basic rhythm test. It had no complete loop, progression or reason to try another song.

The rebuild adds training, song selection, beatmaps, approach animations, scoring, combos, grades and results. A heuristic fallback keeps the game playable when no trained model exists yet.

Where it started

The Python + Unity prototype

The original research build started at roughly 180 ms of latency. After shrinking buffers and simplifying the pipeline, it reached 45 ms with 92% classification accuracy.
