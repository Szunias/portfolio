The game

A rhythm game that has to learn the player first

Kick, snare and hi-hat do not sound the same from every person or microphone. A fixed set of rules would work for me and fail for somebody else, so Transientica begins with a short training session: ten recorded examples of each sound, from the player's own mouth and microphone.

Once the model knows your sounds, the game can focus on the familiar rhythm-game questions: did you perform the right sound, and did it land close enough to the beat?

From microphone to judgement

What happens after you make a sound

The entire path now runs inside Unity. There is no Python process, OSC connection or external machine-learning package between the microphone and the game.

Follow one snare hit from the microphone to the score.

The microphone writes continuously into a pre-allocated ring buffer. An onset detector looks for a sudden rise above the room's noise floor, then sends a 512-sample window through my FFT.

From that window I measure spectral centroid, rolloff, flux, zero-crossing rate, RMS, attack time and flatness. KNN compares those seven values with the examples recorded during training and returns the closest sound class.

Finally, the game matches the hit to the nearest note using Unity's audio clock. It backdates the onset by roughly 5.8 ms for the analysis window, then judges both the sound and its timing.

Signal path Microphone → onset → 512-sample FFT → 7 features → KNN → nearest note → score.

Making it feel fair

Classification is only half the problem

A correct snare still feels wrong if the game reacts late or judges microphone delay as a bad performance.

Perfect is ±60 ms, Great is ±130 ms and Good is ±200 ms. Anything farther away becomes a miss.

Those windows run on AudioSettings.dspTime, not the visual frame rate, so the judgement is not limited by when Unity happens to draw the next frame.

Before playing, the user can beatbox along with calibration clicks at 100 BPM. The game measures the recurring offset and stores it; manual adjustment is available in 1 ms steps.

The combo multiplier grows from 1× to 8×, while the final result ranges from F to S. Notes are pooled ahead of time so spawning them does not allocate during the song.

Architecture change

Why the research prototype was not enough

The first version proved that beatbox classification could drive gameplay. Turning that proof into a standalone game required a different architecture.

One executable, retrainable in the game

The prototype analysed audio in Python, classified it with an SVM and sent results to Unity over OSC. I rewrote the FFT, feature extraction and classifier in C#, then replaced the SVM with inverse-distance KNN (K=5). Training now stores the player's normalized examples as readable JSON, so it can run between rounds without Python, scikit-learn or a local network connection.

The same rebuild added the missing game loop: song selection, beatmaps, approach animations, scoring, combos, grades and results. A heuristic fallback keeps the game playable before a personal model has been trained.
