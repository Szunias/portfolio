Introduction
"Shadow Frames" is a short, single-player psychological black-and-white horror game set in a 1960s pub environment. In this pub people have reported missing items, glasses, cutlery and plates suddenly falling off the tabletops and sightings of mysterious and unexplained shadows.
The player steps into the shoes of a curious investigative reporter, drawn by the consistency of these chilling accounts. The player’s task is to observe, capture, and connect the inexplicable anomalies that haunt the pub to unravel the mystery around them.
This document outlines our chosen development stack, project settings, folder structure and naming conventions as well as the reasoning behind them.


Target Audience

This game is designed for fans of short indie horror games - such as the “I’m on Observation Duty”  franchise, “Chilla’s Art” short horror games, Iron Lung -  and specifically those fans who enjoy horror games that feature unsettling, atmospheric gameplay with environmental storytelling and recourse-based horror mechanics. It is also meant to be enjoyable to streamers who focus on playing horror games and livestreaming their reactions of playing a certain game for the first time. 
The target audience age range is 15-35, since the game deals with horror and mature themes (including alcoholism and depression), and is set in a bar.  Players within this age bracket are often drawn to games that offer deeper narrative meaning, emotional atmosphere, and unique mechanics.

Target Platform
The target platform is PC with a Windows 11 OS. The game will require a keyboard and mouse.
The target resolution for the game is 1440p, and we want a sustained 60 FPS as absolute minimum. We will set the Medium scaling quality setting as the default but may raise it if we can keep the FPS at the desired level.

In order to achieve the FPS we desire, we may have to limit our use of ambient occlusion, volumetric fog, use of transparent textures and reflections. We will be disabling Nanite and Lumen as much as possible, as they do not fit art style and will impact performance.

Development Stack
Unreal Engine 5.5
During the prototyping phase, we tested the implementation of the basic mechanics, audio, and visual style in both Unreal and Unity engine: the prototypes worked in both engines, and the only notable difference was that the Unity Art/Light test offered a stable 45 FPS on the lowest-spec machine we had, and Unreal Art/light test had a stable 59 FPS on that same machine.
We have chosen to use the Unreal Engine for the following reasons:
We want the game to run well on lower-spec machines – preferably lower than the minimum targets set out in this document. The Lighting/Art prototypes suggest that Unreal will be more performant, as it had the higher stable FPS.
Our game’s visual style is semi realistic and relies heavily on lighting and the metallic/roughness texture rendering to be legible to the player and create the desired mood. Unreal’s rendering and lighting capabilities are superior, even if we opt out of many features for the sake of performance, and setting up post-processing effects is more straightforward.
As we only have two artists on the team, we will be using asset packs to fill out our environment, and Unreal has Fab, which is a large asset database that we can draw on for what we need.
One of the main mechanics of the game requires a lot of interaction with UI elements, and it is very easy to implement this in Unreal due to its UMG and widget system.
The majority of the team is more familiar with Unreal than Unity; it would be inefficient to teach them a new engine, especially as neither of the artists is familiar with it and would not be able to help the other. Additionally, the blueprint system of Unreal is simpler for artists to grasp and use if they want to quickly set up animations, visual effects, and so on. 
Using Unreal does add the complexity of using C++ as the programming language, but both of the programmers in the team are comfortable with using C++.

External Assets
The criteria for choosing an existing asset to add are:
It fits the environment of the game: it matches the time period, materials, architecture/culture style of the region.
It fits the shape language and modelling style as described in the art bible.
Processing an asset will happen as follows:
The asset is downloaded is an FBX file and imported into a Blender scene.
The topology is assessed visually and by checking the poly count. If there are too many polygons, the Retopoflow add-on will be used to alter the asset until it is under the polygon limit – ideally, it should be significantly lower than the limit without losing the desired details. For non-hero props, the limit is 1k polygons; there may be some exceptions for larger assets. The polycount is determined based on how big the asset is in game as well as how many times it is featured in the scene. A big asset will use a higher polycount than a small asset because it takes more space in the scene. 
The model is then unwrapped in one of two ways:
Unique texture: It will be unwrapped with the expectation of being textured manually and having its own custom material.
Trim/tileable texture: It will be unwrapped using one of the trim/tileable texture layouts.
The asset will be exported as FBX to be imported into Substance Painter – in Substance Painter, make a new file and import the FBX using DirectX. Do not use OpenGL.
 
Bake the model using the lowpoly model if a high poly model is not available. We do this because our texturing tool needs access to a normal map in order for the generators to work. When using existing assets, we can use the non-optimized as high poly and our reworked version as low poly, if the asset came with a normal map, we can also import that one if the UVs were not altered. Both unique and tiled textures need a normal map, but only the unique ones need to be baked as the tiled material already has its own normal map. 
Use the “SF_Base” smart material located in the ArtAssets folder in the depot.
Do a manual pass on texturing, following the art bible guidelines.
Export the textures following the unreal engine (packed) format. with the (Ambient) Occlusion, Roughness and Metallic packed into one texture:

The mesh and textures must then be imported into the Unreal project, following the standard folder structure. The exported FBX and texture files do not get added to the depot.

Export File Types
For textures, we use TGA and PNG, depending on use case: for 3D models we will be using TGA for the color map, and for the ORM and Normal maps we will be using PNG; for UI elements it will all be PNG files made in Adobe Photoshop.
The TGA format has a fourth channel to handle the alpha, while PNG stores the alpha within “unused” locations inside the RGB channels. This makes TGA files bigger and requires manually setting up and handling the fourth channel; however, it avoids certain visual artefacts when 3D meshes are rendered (such as white contour edges), and allows for fancy shader trickery such as adjusting cutoff or alpha values.
The white border can also be an issue for UI when using PNG textures, but there is a setting in Unreal engine to deal with that without having to use TGA files or change the textures manually.

All 3D models will be made in Blender (.blend) and exported as FBX; animations and rigs will also be exported in the FBX file along with the model. 

For the texturing, we will be using Substance Painter, and exporting the textures as TGA for the color, and PNG for ORM and normal maps. 

Grid Scale for Tiling Assets
For modular assets that are intended to tile, we will use a grid size of 0.5m: so, an acceptable asset may be 1.0m or 3.5m, but not 2.25m.

Mesh Pivot Points
Meshes that are not modular must have their pivot set to 0,0,0 in Blender, and the mesh itself should be standing ‘on top’ of that point; the lowest vertex of the mesh should not be lower than 0.
Modular assets will have the left bottom corner snapped to 0,0,0 - this way the left corner will be used as the pivot point in engine, allowing for easy snapping. 
Exported meshes should not have any scale, rotation or transformation values when exporting.

Programming Specifics 
This is a C++ Unreal project, so the majority of the programming will be done in code files and not visual scripting; game logic will be fully done via code, and implemented into the game via blueprints that inherit from the C++ code classes, but add on no further game logic functionality by themselves – they are simply to provide an interface for setting default values to various parameters, adding purely visual elements (meshes, effects, animations). 
Photoboard 
The photoboard will be implemented using the UMG – it will be a widget that exists in the game in the form of a Widget Component on an actor blueprint, and will be added to/removed from viewport when the player interacts with that actor by approaching it and pressing a button. This will also swap the player input mode between regular input, and board-interacting input (selecting photos, deleting them, moving them around the board). 
The interactions with the photos will be implemented by making a separate widget for the photos, which has overrides for the functions “On Mouse Button Down”, “On Drag”, “On Drop”, and anything else that may be relevant; these overrides can be implemented in either the base C++ code class for the widget, or in the visual scripting part of the widget blueprint.
The logic to check whether the photos are placed in the correct spots will be handled via code in the base C++ class for the photoboard, which will have a function to compare the actual contents of the photo slots to a list of the desired contents, and will be executed after a drag operation on a photo gets finished.
Picture taking 
Taking photos is implemented fully via code and is executed when the player presses a specific button. A UsceneCapture2DComponent and a Render Target are used to render the scene to a new PNG file that is saved locally on the computer. That file is used to both spawn a new dynamic material instance, which is used when spawning a temporary mesh that display the photo to the player, and also to set the brush component of one of the photo widgets, so the photoboard can display all taken photos.
The saved photos persist past the game being stopped, so we are limiting their size and resolution to the smallest possible amount while preserving enough detail that they are useful for the player, and there will be a limit on the maximum number of photos a player can take and store.
Programming Guidelines
We will adhere to the Unreal Engine C++ coding standard. The full guidelines can be found here: https://dev.epicgames.com/documentation/en-us/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine?application_version=5.5. 
Below is a list of selected rules we will pay special attention to as courage to keep our code clean, clear, and organized.

Language conventions
All code and comments in the code files should use US English spelling and grammar, e.g. color and not colour, behavior and not behaviour. This also applies to file/asset names across the project.

Naming conventions
Names for variables, methods, and classes must be:
Clear
Unambiguous
Descriptive
All names are in PascalCase, multiple words concatenated together, without hyphens or underscores, and should avoid abbreviations. However, extremely common acronyms, like UI or HUD, are exceptions to the abbreviation and PascalCase rules – they can stay abbreviated and uppercase when used. 
Good
AllPhotos = PlacedPhotos + ReservedPhotos

Bad
ap = pp + rp

Variables used for iteration in for-loops are allowed to be lowercase single letter.
for(int i{0}; i < TotalPhotos; ++i)

Private and protected member variables are prefixed with m_ e.g. m_MyVariable.
protected:
int m_PhotosTaken{0];
Type names must have a single-letter upper-case prefix to distinguish them from variable names e.g. FThing as a type name, Thing as an instance of type FThing. 
APhotoboard m_Photoboard{];

Class Structure
All classes must be organized as follows: after the GeneratedBody() comes the public section, then the protected section, then the private section. In each section, the functions come before the variables. A blank line must be left between each section for visual clarity.
class PROJECTNAME_API AMyActor : public AActor
{
    GENERATED_BODY()
    
public: 
    AMyActor();
    float MyFloat;

protected:
    void Foo();
    int m_MyInt;

private:
    void Bar();
    FString m_MyString;

};

Syntax
Class members should almost always be declared private unless they are intended to be part of the public/protected interface of the class. 
Class members used by child classes should be marked protected. 
Class members that need to be accessed from outside the class should be marked public. If the getter and/or setter of a variable are non-trivial, that variable should remain private and only its getter/setter should be public. In the case of trivial getters and setters, the variable should be made public.




Good
class PROJECTNAME_API AMyActor : public AActor

    int m_IntToAlter;

{
    
public:

Prefer default member initialization where possible.

Keep methods concise – if a method is getting too long, split it into sub-methods.
Mark functions as override and classes as final wherever applicable.
Do not use auto unless:
When binding a lambda to a variable.
For iterators IF the type is verbose and would make the code harder to read.
In template code where the expression type cannot be easily identified.
Avoid usage of the C++ standard library. Unreal has its own implementation of most of these functions: for example, Unreal has MoveTemp instead of std::move. Avoiding the standard library is especially important in the cases of strings and containers.
Const correctness
Pass function arguments by const pointer or const reference if those arguments are not intended to be modified by the function.
Flag methods as const if they do not modify the object.
Use const iteration over containers if the loop isn't intended to modify the container.
void SomeMutatingOperation(const TArray<Int32>& InArray)
{
    // The InArray will not be modified, so it is marked const
}
    
void FClass::Foo() const
{
    // This code will not modify the FClass object it is invoked on.
}

for (----- : Container)
{
    // The body of this loop will not modify the elements of the container
}

Braces always go on new lines. Always include braces in single-statement blocks. This applies to if-else statements as well. 
Good
int32 GetSize() const
{
    return Size;
}
Bad
int32 GetSize() const { return Size; }

A multi-way if statement should be indented with each else-if indented the same amount as the first if; this makes the structure clear to a reader.
Good
if()
{
}
else if()
{
}


Always include braces in single-statement blocks.
if (bThing)
{
    return;
}

Function declarations should have at least one blank line between them. 
Good
void AGrandmaCharacter::Foo()
{
}

void AGrandmaCharacter::Bar()
{
}
Bad
void AGrandmaCharacter::Foo()
{
}
void AGrandmaCharacter::Bar()
{
}

Switch case statements should explicitly label that a case falls through to the next case, unless it is an empty case.

Physical Dependencies
All headers should protect against multiple includes using #pragma once.
Forward declarations are preferred to include headers, and if headers must be used, they must be included when absolutely necessary and as specifically as possible. Do not rely on headers included in other headers. 
Avoid prefixing file names if possible.



Comments
Only use comments when necessary – if they do not provide extra information that is not given by the code, they do not need to exist. Focus on writing self-documenting code. Rewrite bad code rather than relying on comments.
Good

Good

Bad

General
Use int32 instead of int for all serialized variables, e.g. on UPROPERTY designated variables.
Always use TEXT() macro around string literals.
Leave a blank line at the end of the file.
Use intermediate variables to simplify complicated expressions.
Good
const bool variablesABSame = variableA == variableB;
