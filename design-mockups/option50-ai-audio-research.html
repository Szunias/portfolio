The Research

What I Tested and Why

Every gunshot, footstep, and explosion in a game is a pre-recorded WAV file. Hundreds of them per project. AI could generate these on the fly - so every sound would be different, no gigabytes of samples shipping with the game. The catch: latency. Games run at 60fps, that's 16.7ms per frame. If a sound shows up even 100ms late, players notice. I wanted to know exactly how slow these models are and whether there's a workaround.

I built a system where Unreal Engine 5 talks to a Python backend over WebSocket. The Python side loads AI models, juggles VRAM on an 8GB GPU, and sends back raw PCM audio. I compared three approaches: procedural DSP (basic synthesis, instant), local GPU inference (AudioGen and MMAudio in two sizes), and a cloud API (ElevenLabs). I also tried TangoFlux but it wouldn't even start - missing CUDA kernels for the Blackwell architecture on my RTX 5070.

24 prompts across 5 sound categories - footsteps, impacts, UI clicks, ambience, and music. Each prompt tested with all 5 methods, repeated 5 times: 600 generations total. On top of that I ran 500 attempts per method just to see how often things break.

Results

Measured Latency

Procedural DSP

15 - 25ms end-to-end
Quality: 2.4/5 · 0% failure rate

Basic synthesis - no GPU, no network, just math. The only method that actually hits the latency target on the first try. Sounds synthetic and a bit "video gamey" but it never fails and never lags. I use it as the fallback when AI models are busy or crash.

AudioGen

2,100 - 2,800ms end-to-end
Quality: 3.6/5 · 2.4GB VRAM · 9.2% failure rate

Meta's text-to-audio model (autoregressive). Most reliable of the local models - generation times don't jump around much and the quality is OK for environmental stuff. Cold start adds another 1-2 seconds on top. I'd describe the output as "reliable but plain." Good enough for prototyping.

MMAudio Large

2,600 - 3,400ms end-to-end
Quality: 3.9/5 · 3.1GB VRAM · 13.8% failure rate

Flow-matching model. Best sounding of everything I ran locally - good textures, natural feel. But it eats 3.1GB of VRAM, which means nothing else fits in memory alongside it. Every model swap costs 2-4 seconds. And the duration control is inconsistent: I'd ask for 1 second and sometimes get 3. Worth it for impacts and music where you have time to wait.

MMAudio Small

1,400 - 1,900ms end-to-end
Quality: 3.5/5 · 1.8GB VRAM · 7.2% failure rate

The sweet spot. Faster than the Large version, still sounds decent, and at 1.8GB it can actually share VRAM with AudioGen - no swapping needed. Also the only model that generates faster than playback for 10-second clips (RTF < 1.0), so it can stream ambience in real time. If I had to pick one model for a real game, this is the one.

ElevenLabs Cloud

1,800 - 3,500ms end-to-end
Quality: 4.3/5 · 0GB VRAM · 4.8% failure rate

Commercial API. Sounds the best by a clear margin - sharp transients, natural clarity. But the latency swings wildly depending on their server load that day. No GPU needed on your end, though you do need internet. I'd use it for stuff you can pre-generate: cutscene effects, signature weapon sounds, moments where quality really matters and you're not in a rush.

With Caching

35 - 90ms delivery
95 - 98% latency reduction

Sounds I've already generated get stored in memory, keyed by a SHA-256 hash of the prompt. Next time the same sound is needed: instant. On top of that, client-side DSP (pitch shift, volume, reverb, filtering) turns one cached sample into 10+ different-sounding versions. This is what made the whole project work.

How It Works

The Caching Strategy

01

Pre-Generation

While the player is on a loading screen or walking into a new zone, generate the sounds they'll probably need next.

02

Prompt Hashing

SHA-256 hash of normalized prompt + model + duration + sample rate. Same request always hits the same cache entry.

03

Cache Hit

Sound plays from PCM cache in 35-90ms. Client-side DSP adds variation: pitch shift, filtering, reverb, volume randomization.

04

Background Refill

After a sound plays, the system quietly generates a new variation in the background. Old entries get kicked out when memory hits 500MB. Disk cache survives between sessions.

Engineering

Problems I Solved

Game Thread Bottleneck

Unreal requires all UObject creation (including USoundWave) on the main Game Thread. But WebSocket callbacks arrive on a background thread. If you just try to create a SoundWave from the network callback, it crashes instantly. I used FFunctionGraphTask to push the PCM data to the Game Thread where it's safe to create the SoundWave. Works fine with 50+ sounds coming in at once.

VRAM Budget Management

My GPU has 8GB of VRAM. UE5 alone takes 4-5GB just for rendering. That leaves maybe 3GB for AI. Only AudioGen + MMAudio Small fit together - everything else needs swapping. So I built a VRAM manager that checks free memory via NVML, kicks out the model you haven't used recently, and loads what you need. The swap takes 2-4 seconds. For models you use a lot, I added a "sticky mode" that keeps them in memory.

Failure Handling

These models fail more than you'd expect: 5-14% of the time, depending on the model. Sometimes the output is just silence. Sometimes the generation takes too long and times out. Sometimes CUDA runs out of memory and crashes. A game can't just freeze when that happens. My fallback chain: retry with a different seed, try a different model, play procedural DSP instead, or just skip the sound. A mediocre sound right now beats a perfect sound 3 seconds late.

The Bleeding Edge Penalty

TangoFlux was supposed to be the fast one - a diffusion model optimized for low latency. It didn't even start. PyTorch 2.4 with CUDA 12.4 didn't have compiled kernels for the RTX 5070's Blackwell architecture (sm_120). I tried building from source but hit Windows toolchain issues. Wasted two days on it. Takeaway: if you're making a game, use models that have been out for 6+ months. Bleeding-edge research code breaks on real hardware.

The Insight

It's Not About Speed

None of the AI models came close to real-time on the first try. The fastest local model (MMAudio Small) still needed 1.4 seconds - about 85× slower than a single game frame. I'd added caching early just to avoid regenerating the same sound twice. Then I checked the delivery times in the logs: 35-90ms. That's fast enough.

So I stopped trying to make AI faster and started thinking about when to generate. Loading screens. Zone transitions. Quiet moments while the player is reading a menu. Generate the footsteps before the player starts walking. By the time they actually move, the sound is already sitting in memory.

Generative audio is not about making generation faster - it's about hiding generation latency.

Right now this works for prototyping, ambient audio, and games where you can predict what sounds the player will need. It doesn't work for competitive shooters where every millisecond counts, or for mobile where there's no GPU to run inference on.

Conclusion

The Short Answer

Without workarounds: No. All tested methods exceed 150ms on first generation.

With caching: Yes. Cache hits come in at 35-90ms - within interactive budgets.

With pre-generation: Yes. If you can predict the sound, the player feels zero delay (<10ms from local engine buffer).

No single model wins everything. Procedural DSP is fast but sounds fake. ElevenLabs sounds great but you can't rely on the latency. The real answer is you mix them: use the right model for the right sound, cache everything you can, and have a fallback ready for when things go wrong.
