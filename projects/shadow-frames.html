Project Overview

Black-and-white horror game where you photograph paranormal events in a 1960s Irish pub. Sound is your main tool for finding anomalies.

CONCEPT

Core Concept

You have a Polaroid camera and 25 shots across 5 cartridges. Anomalies happen every 30-50 seconds. Glasses levitate, shadows move on their own, chairs spin. Audio cues tell you where to look: a glass clinks, footsteps echo from nowhere, a chair scrapes across the floor. Without sound, you're blind. Once you capture the evidence, arrange the photos on a corkboard in order to piece together what's happening.

🎧 Headphones highly recommended. The game uses binaural audio for precise 3D positioning. Stereo speakers won't give you the directional accuracy you need.

AUDIO DESIGN

3-Stage Anomaly Detection

Every anomaly triggers three audio layers:

Alert (0.5s): Static burst marks the spawn
Hint (1-2s): Directional sound points you there
Presence (loop): Sustained until captured

No visuals, no UI markers, just sound. Audio is the detection system.

Footstep System: Surface Detection & Audio Routing

Physical material detection drives dynamic audio switching for realistic surface-based footsteps.

WHAT

System detects surface type under player and automatically switches appropriate footstep sounds in Wwise.

HOW

C++ component performs line trace downward, detects Physical Material, and maps it to Wwise Switch name.

WHY

Separation of Concerns - C++ handles detection, Blueprint handles audio. Delegates provide loose coupling.

RESULT

Realistic footsteps matched to surface, zero manual switching, easy expansion with new materials. 

FName UFootstepComponent::DetectSurfaceType() const
{
    const AActor* Owner = GetOwner();
    const UWorld* World = GetWorld();
    if (!Owner || !World) return FName("Concrete");
Null Safety
Validates owner and world exist before tracing. Returns "Concrete" as safe fallback.


    FHitResult Hit;
    const FVector Start = Owner->GetActorLocation();
    const FVector End = Start - FVector(0.f, 0.f, TraceDistance);
Trace Setup
Creates downward line trace from player position to detect surface below.


    FCollisionQueryParams QueryParams;
    QueryParams.AddIgnoredActor(Owner);
    QueryParams.bReturnPhysicalMaterial = true;
Query Config
Configures trace to ignore player and return Physical Material data for surface detection.


    bool bHit = World->LineTraceSingleByChannel(
        Hit, Start, End, ECC_WorldStatic, QueryParams
    );

    if (bHit && Hit.PhysMaterial.IsValid())
    {
        return MapSurfaceToWwiseSwitch(Hit.PhysMaterial->SurfaceType);
    }
Surface Mapping
Maps Unreal's SurfaceType enum to Wwise Switch names (Wood, Tiles, Concrete, etc.).


    return FName("Concrete");
}

Player Audio System: Delegate-Based Communication

Clean separation between player actions and audio responses using Blueprint delegates.

WHAT

System connects player actions (camera shot, zoom, photoboard entry) with appropriate audio events in Wwise. Each player action automatically triggers corresponding sound.

HOW

PlayerCharacter in C++ defines multicast delegates. When player performs action, delegate is broadcast. Blueprint Audio Manager listens to these delegates and calls appropriate Wwise Events.

WHY

Delegates provide loose coupling - PlayerCharacter knows nothing about audio, Audio Manager knows nothing about player logic. Each system can be tested and modified independently.

RESULT

Clean architecture, easy addition of new audio actions, zero hardcoded calls. Audio designer can modify audio without touching player code.

Click to enlarge

PlayerCharacter.h: Delegates

WHAT: Definition of multicast delegates for player actions that trigger audio events.

HOW: DECLARE_DYNAMIC_MULTICAST_DELEGATE creates delegate that can be broadcast from C++ and listened to in Blueprint. UPROPERTY(BlueprintAssignable) allows binding in Blueprint.

WHY: Multicast delegates allow multiple listeners (e.g. Audio Manager) to react to one action. Dynamic delegates work with Blueprint, giving audio designer full control without modifying C++ code. 

// PlayerCharacter.h - Delegate declarations for audio events

// Defines three multicast delegates for player actions
// Dynamic = works with Blueprint, Multicast = multiple listeners

DECLARE_DYNAMIC_MULTICAST_DELEGATE(FOnCameraZoomInDelegate);
DECLARE_DYNAMIC_MULTICAST_DELEGATE(FOnPhotoboardEnterDelegate);
Delegate Declarations
Creates three event types for player actions. Dynamic delegates work with Blueprint, multicast allows multiple systems to listen simultaneously.

Dynamic Tension System: RTPC-Driven Ambience

Progressive ambient intensity scales with game state - photos placed on board increase tension.

WHAT

System dynamically changes ambient intensity based on number of photos placed on board. More photos = more tense atmosphere. RTPC value 0-5 controls ambient layers in Wwise.

HOW

PhotoboardWidget tracks number of important photos. When player places photo, UpdateAmbientRTPC() finds AkAmbientSound actor and sets RTPC value. Wwise automatically crossfades between ambient layers.

WHY

RTPC gives smooth transitions between tension states. no jumps. I can precisely control in Wwise how each ambient layer responds to RTPC value. Full control over emotional progression.

RESULT

Smooth tension progression, zero audio jumps, easy curve modification in Wwise. Atmosphere automatically adapts to player progress.

PhotoboardWidget.cpp: RTPC Update

WHAT: Function updates RTPC value in Wwise based on number of photos placed on board.

HOW: Validates world exists, then finds AkAmbientSound actor by tag 'AmbientProgressive' (more efficient and reliable than name string search). Sets RTPC value (0-5) corresponding to number of important photos. Wwise automatically crossfades between ambient layers.

WHY: RTPC allows smooth transitions between tension states. Audio designer can precisely control crossfade curves for each layer in Wwise, giving full control over emotional progression without code modifications. 

// PhotoboardWidget.cpp - Updates ambient RTPC based on photos placed

void UPhotoboardWidget::UpdateAmbientRTPC()
{
    // Null safety checks - validate RTPC and world exist
    if (!PhotosOnBoardRTPC) return;
    const UWorld* World = GetWorld();
    if (!World) return;
Null Safety
Validates that RTPC parameter and world context exist. Early returns prevent crashes from missing setup.


    // Find actor by tag (more efficient than name search)
    // Tags are less error-prone than string comparisons
    // NOTE: Could be cached for better performance
    AActor* TargetActor = nullptr;
    TArray FoundActors;
    UGameplayStatics::GetAllActorsOfClass(World, AAkAmbientSound::StaticClass(), FoundActors);
Actor Search
Finds all AkAmbientSound actors in the level. This could be cached for better performance in frequently called functions.


    for (AActor* Actor : FoundActors)
    {
        if (Actor && Actor->ActorHasTag(FName("AmbientProgressive")))
        {
            TargetActor = Actor;
            break;
        }
    }
Tag-Based Lookup
Searches for actor with "AmbientProgressive" tag. Tags are more reliable than name comparisons and easier to maintain.


    // Set RTPC value - Wwise crossfades ambient layers automatically
    // Creates smooth tension progression as photos are placed
    if (TargetActor)
    {
        UAkGameplayStatics::SetRTPCValue(
            PhotosOnBoardRTPC,
            ImportantPhotosAlreadyPlaced,
            0,  // Interpolation time (immediate)
            TargetActor
        );
    }
RTPC Update
Sets Real-Time Parameter Control value in Wwise. Value represents number of photos placed (0-5). Wwise automatically blends ambient layers based on this parameter.

Wwise Architecture: Switch Containers & Photoboard Integration

Continuation of the RTPC system - Switch Containers in Wwise respond to photos collected on the photoboard, creating dynamic ambient layers.

WHAT

Switch Container system in Wwise responds to the number of photos collected on the photoboard. As player collects more photos, different ambient layers are activated through Switch Containers, working in conjunction with the RTPC system.

HOW

The RTPC value from PhotoboardWidget (0-5 based on photos) drives Switch Container selection in Wwise. Each Switch state corresponds to different ambient layers. Wwise automatically crossfades between layers as photos are collected.

WHY

Switch Containers provide discrete layer control, RTPC handles smooth transitions. This combo lets me do both structural changes (different ambient sets) and smooth intensity progression. I control each layer's response in Wwise.

RESULT

Dynamic ambient system that responds to player progress through photoboard collection. Additional layers and complexity are in development for final release.

Enemy Presence Audio System

Dynamic audio system that responds to enemy proximity. Creates tension through dread layers and stressed breathing.

WHAT

System tracks enemy distance and triggers audio layers. Closer enemy = more intense audio. Dread ambience and breathing stress scale with proximity.

HOW

OnProximityChanged() receives proximity value (0-100%), starts/stops dread layers, updates RTPC for intensity, adjusts breathing stress. All validated with null safety checks.

WHY

Real-time audio response creates psychological tension. RTPC allows smooth intensity transitions instead of abrupt changes. Separate breathing layer reinforces player's fear state.

RESULT

Audio intensity scales smoothly with danger level. Player feels increasing dread as enemy approaches through layered ambient sounds and stressed breathing.

Ambience Zone System

Location-based audio that changes as you move through different areas of the pub.

WHAT

5 distinct zones with unique ambient soundscapes: Main Bar, Back Room, Bathroom, Hallway, Storage. Each has specific audio atmosphere.

HOW

Trigger volumes detect player location. On zone enter, fade out previous ambience and fade in new zone's layers. Smooth crossfades prevent audio jumps.

WHY

Location-specific ambience grounds player in the space. Each room feels acoustically different, reinforcing the pub's layout and atmosphere.

RESULT

Seamless audio transitions between zones. Player subconsciously understands pub layout through sound design. Each area has distinct acoustic identity.

Main Bar Zone

Bar chatter, glass clinks, creaking wood. Primary gameplay space ambient.

Back Room Zone

Muffled ambience, distant echoes. Isolated, claustrophobic atmosphere.

Bathroom Zone

Spatialized toilet drip (3D positioned), leaky faucet. Reverb-heavy environment.

Hallway Zone

Transitional space. Wind through cracks, distant footsteps, subtle tension.

Storage Zone

Dead silence with occasional object shifts. Oppressive quiet before anomaly events.

Spatial Audio Implementation: Bathroom zone demonstrates HRTF spatial audio capabilities. Toilet drip positioned at specific 3D coordinates with distance attenuation (0-500 units). Faucet leak uses separate AkAmbientSound with realistic falloff curve. Players can accurately locate sound sources through headphones, reinforcing environmental realism.

Anomaly Audio System

3-stage detection system for 10 different paranormal anomaly types with unique audio signatures.

WHAT

3 detection stages: Far (general alert), Medium (directional cue), Close (precise location). 10 anomaly types including Levitating Glass, Shadow Movement, Spinning Chair.

HOW

Distance-based RTPC drives audio intensity. Directional audio guides player to anomaly. Each anomaly type has unique sound signature for identification.

WHY

Audio is the primary detection mechanic. Without sound, finding anomalies is nearly impossible. Layered approach (alert → guide → confirm) creates engaging gameplay loop.

RESULT

Players rely on audio cues to locate and identify anomalies. Sound design is functional and atmospheric - drives core gameplay while building tension.

Problems encountered during development and how I addressed them.

Workflow Optimization Tools

Problem:

Working in a multi-institutional collaboration with students, workflow issues frequently disrupted development. Wwise integration would break after Perforce pulls, and Unreal Engine compilation times were causing significant downtime.

Solution:

Created Wwise Unreal Fixer and Unreal Engine Rebuilder tools to streamline the workflow. While not fully independent work (collaborative effort), these tools were primarily developed to help students work more efficiently. The Wwise Fixer automatically restores broken Wwise integration after Perforce pulls, and the Rebuilder automates the compilation process to reduce downtime.
